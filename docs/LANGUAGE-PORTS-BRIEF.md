## Source of truth (read first)
- **`NAMZ-FORMAT.md`** — the wire format: magic `NAMZ`, 1-byte version/codec/dtype/flags, `u16` metaLen +
  meta JSON, then body = `u32` skeletonLen + minified JSON skeleton (each numeric `"weights"` array
  replaced by its ordinal integer index) + `u32` numArrays + `u32` lengths[] + payload: float32 (dtype 0),
  or IEEE half (dtype 1, lossy, written only on request — "The float16 dtype (`.nam16z`)"). Integer fields
  are little-endian; the float payload is IEEE-754 little-endian. flags bit0 = payload byte-plane shuffled
  (4 planes for float32, 2 for float16).
- **`include/namz.h`** — the C++17 reference impl (MIT). **`cli/namz.cpp`** — the CLI (`encode`/`decode`/
  `map`/`verify`).
- **`conformance/`** — the CROSS-LANGUAGE CONTRACT (a TCK): `vectors/*.nam` → `vectors/*.namz` golden
  pairs, `invalid/*.namz` must-reject blobs, and `manifest.json`. See `conformance/README.md`. This
  already exists; regenerate with `python3 conformance/generate.py build/namz` if you change the format.

## What .namz is
A `.nam` is JSON whose weights are ~20-char decimals the engine loads as float32 anyway. `.namz` stores
each weight as a 4-byte float32: ~5.5× smaller, bit-exact to float32, deterministic (no compression →
byte-identical across runs / platforms / languages). A readable metadata header exposes tone/device/gear
without decoding weights. On explicit request only, a file stores each weight as the IEEE half nearest its
float32 instead (dtype 1, `.nam16z`): half the payload, and LOSSY.

**Float16 in the ports.** The js and python ports carry it as of 1.3.0, as the reference does as of 4.4.0:
`pack` writes dtype 1 only when its options ask (`{ dtype: DTYPE_F16 }` / `PackOptions(dtype=DTYPE_F16)`,
mirroring `PackOptions::dtype`), rounding on the bits (`halfOf`: ties to even, subnormals kept, |w| ≥ 65520
refuses the whole `.nam`); `unpack` reads either dtype by the dtype byte and widens each half exactly
(`floatOfHalf`), with every reader rule holding over a payload of `sum(lengths) * 2` bytes. Their CLIs take
`--f16` with the reference's name rule (`--f16` writes only a `*.nam16z`, a `*.nam16z` only with `--f16`). A
new port carries float16 from its first release.

## Testing model (the whole point)
Every port runs the **shared conformance vectors** (`conformance/manifest.json`, four sections):
1. `valid`: `encode(input, options)` **byte-matches** the expected `.namz` (options: `shuffle`, `set`,
   `dtype` — 1 is float16, whose golden is a `.nam16z`), and `decode(expected)` reproduces the weights
   **bit-exact** (float32; for dtype 1, the half nearest each input float32, widened);
2. `invalid`: every listed `.namz` is **rejected** cleanly by decode (never crash/hang);
3. `decodeOnly`: every listed `.namz` — one `pack` never writes — decodes to **exactly** its `.nam`, byte for
   byte (the placeholder literal as written, the reference's own double digits);
4. `invalidNam`: every listed `.nam` is **refused** by encode with its `dtype` (the float16 ones pack fine as
   float32: a weight past half's range).

Plus a **local property fuzz** per language (N random finite float32 → round-trip → bit-exact) and
idiomatic unit tests — but the shared vectors are the guarantee.

### Byte-match gotchas
- Skeleton = **minified JSON, object keys sorted ascending** (nlohmann sorts). JS: `JSON.stringify` doesn't
  sort → custom sorted+compact stringify.
- **Numbers print with nlohmann's digits**, not the language's: Grisu2 (`dtoa_impl` in nlohmann's
  `to_chars.hpp`) is neither always the shortest nor always the closest, and it switches to exponent form
  past 15 integer digits (`1e+15`). Shortest round-trip printers (`repr`, `toExponential`) differ on about 1
  in 400 float32 values — every real capture's `unpack`. Port `dtoa_impl` step for step (64-bit products:
  BigInt in JS, ints in Python); Python's `json.dumps` hard-codes `float.__repr__`, so it needs its own
  serializer. The `decodeOnly` vector `float-digits` and the `valid` vector `skeleton-doubles` catch it. Where a language can't match key order, rely on decode-bit-exact +
  idempotence and document it — never fake a golden.
- Endianness: write `u16`/`u32` little-endian explicitly. Float payload IEEE-754 LE (numpy
  `astype("<f4").tobytes()`).
- Reproduce the byte-plane **shuffle** exactly (`shuffleInto`/`unshuffleInto` in `namz.h`).

## Versioning
The C++ reference is **v1.0.0**. **Each language port versions INDEPENDENTLY** — its own semver, its own
tag namespace, its own release cadence and registry. (Python `namz` on PyPI, JS `namz` on npm, etc. each
start at their own 1.0.0 when ready.) Do not couple a port's version to the C++ version; couple to the
**format/spec** version instead (the wire `formatVersion`, currently 2).
